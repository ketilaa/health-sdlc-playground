# Skill: Experimental UX

Apply these principles when designing and reviewing UX specifications.

---

## Designer principles

**Colour is the primary language — not a finishing touch.**
Every entity that recurs in the UI (activity type, status, category, state) must have a named colour token. Do not rely on text labels alone to distinguish between things. Define a token system — `--color-long-run`, `--color-intervals`, `--color-sickness-week` — never inline hex values. The developer fills in the actual values; the spec names the tokens and describes their role.

**Default to dark or deep-toned backgrounds for data-heavy UIs.**
Dark backgrounds give colour tokens more contrast and visual impact. Light-on-dark is not a "special mode" — it is a valid default that makes the UI feel intentional rather than blank. Choose it unless there is a specific reason not to (e.g. a feature that lives inside a light-background shell).

**Icons over text labels wherever the concept has a clear visual analogue.**
A running shoe, a leaf, a lightning bolt communicate activity types faster than "Long run", "Restorative run", "Intervals". Specify the icon role and its semantic meaning; do not leave icon choice to the developer's discretion. Icons should supplement or replace labels — not float next to them as decoration.

**Visual hierarchy through contrast, not just size.**
Do not list elements and call that a hierarchy. Describe how importance is communicated: which value is largest, which is muted, which uses the accent colour, which recedes. A spec that says "show distance, duration, and count" is incomplete. A spec that says "distance is the primary value rendered at full opacity with the accent colour token; duration and count are secondary at reduced opacity" is complete.

**"Slightly experimental" is the floor, not the ceiling.**
Push further unless a specific accessibility constraint (contrast ratio, screen-reader ordering) or testability constraint (needs a `data-testid`) blocks it. A design that could have been generated by any generic component library is a missed opportunity.

**Animated or transitional states are encouraged when they reinforce meaning.**
Loading skeletons that pulse, rows that expand with a smooth transition, colour fills that animate in — these are not over-engineering. Describe the intended motion as part of the state definition.

---

## Reviewer checklist

Apply these checks when validating a UX spec. Any failure is a **blocking** issue.

- [ ] Every recurring entity (activity type, status, category) has a named colour token defined in the spec — not described as "a colour" or left to the developer
- [ ] The spec defines a background colour token; "white" or "default" is not acceptable as the background without a rationale
- [ ] Icons are specified for entity types that have a clear visual analogue — text-only labels for recurring types are a gap
- [ ] Visual hierarchy is described in terms of opacity, colour, size, or weight — not just as an element list
- [ ] The spec does not use phrases like "show the activity type" without specifying how it is visually distinguished (colour token, icon, or both)
- [ ] If a loading or transition state is defined, it describes the motion or visual change — not just "show a spinner"
